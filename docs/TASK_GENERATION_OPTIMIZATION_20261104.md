# 任务下发慢与统计冲突：2026-11-04 只读调查和改动

## 线上证据

- `task_generation_jobs.stageEventsJson` 显示今天六个 V4 作业的“生成并分配基础任务”耗时 549–1289 秒，约 28–38 条基础任务/秒；模板加载只占 21–38 秒。
- 两个作业在回测任务写入后、进度 97% 处失败。PostgreSQL 日志分别于 UTC 03:09:23、06:14:16 报 `could not serialize access due to concurrent update`，语句为删除 `scorer_task_stats`；随后的自动回滚也发生并发更新冲突。第二次还出现 `project_task_stats` 更新锁超时。
- `V4_REALISM_1104` 计划 31,540 条，线上只读 `COUNT(*)` 实际为 31,386 条，差 154 条。`V4_CREATIVITY_HIGH_INDEPENDENT_1104` 计划 42,100 条，统计快照显示 42,100 条，但实际明细计数在 15 秒只读超时内未完成，不能把快照当作完整核验。
- `rating_tasks` 有 32 个索引，表本体约 1.6 GB，含索引约 18 GB。数据库未安装 `pg_stat_statements`，无法仅凭现有数据分摊每条 SQL 的耗时。
- 线上 PostgreSQL 容器把 `/var/lib/postgresql` 绑定到宿主机 `/data/sunwenxiu/rating/postgres`；`/data` 是 `fuse.quarkfs_client`，而本机 `/` 是 ext4 且剩余约 425 GB。仓库 `.env.example` 已注明 PostgreSQL 数据目录应放在本机 ext4，不应放在 `/data`。线上 PostgreSQL `shared_buffers=128MB`，容器内存上限 8 GB；数据库累计缓存命中率约 74.31%，`pg_stat_io` 记录大量缓存淘汰。存储和缓存是更优先的性能嫌疑点，但 `track_io_timing=off`，尚无单次 I/O 延迟数据，不能声称已测得提速倍数。

## 本地改动

1. 统计事件刷新读取数据库内的活跃生成作业；跨进程运行器不再被 API 的进程内状态遗漏。
2. 生成作业的最终统计刷新与事件刷新共用数据库事务级锁，并对 `40001`、`40P01`、`55P03` 做最多四次完整事务重试。
3. 最终任务写入完成后若收尾失败，不再自动删除已经下发的任务；作业明确标记“需要核对实际任务及统计结果”，保留七天。
4. 批次日志记录事务启动、任务插入、图片项插入和提交耗时。V4 运行器保留每批 100 条的默认值，可用 `TASK_WRITE_BATCH_SIZE` 在测试环境设为 500 或 1000；应用层上限设为 1000，避免超出 PostgreSQL 参数数量限制。

## 本地隔离库批量实验

本机没有迁移的线上数据，也没有既有 PostgreSQL。另建临时 PostgreSQL 18 集群，加载项目 schema，以 5 万条任务、10 万条图片项为基底；每种批量再插入 2 万条任务和 4 万条图片项，跑两轮。每批使用独立的 `REPEATABLE READ` 事务、两条 `INSERT ... ON CONFLICT DO NOTHING` 和一次提交。结果如下：

| 每批任务 | 两轮耗时 | 平均吞吐 |
| ---: | ---: | ---: |
| 100 | 1.234 秒、1.324 秒 | 15,632 条/秒 |
| 500 | 1.598 秒、1.284 秒 | 13,882 条/秒 |
| 1000 | 1.500 秒、1.400 秒 | 13,792 条/秒 |

本地测试没有复现线上约 230 万条任务、持续评分写入和远程存储条件；绝对吞吐不能外推。此次结果不支持直接提高线上默认批量，因此仅保留配置入口和分段计时，待有接近线上负载的测试库再决定是否调大。

另以真实 `generateSubjectTasks` 代码在同一本地库运行，每个配置生成 1000 条基础任务：100 条/批耗时 132 毫秒，500 条/批 133 毫秒，1000 条/批 203 毫秒；三次任务数、分配数与统计数均为 1000。并发更新测试实际触发 `40001`，新逻辑重试一次后，项目统计和 `rating_tasks` 明细均为 170000 条。回滚测试确认已完成任务不会被删除，自动回滚返回失败并要求人工核对。

## 上线前与灰度验收

1. 优先准备 PostgreSQL 数据目录迁移：确认 `/var/lib/rating/postgres` 位于 ext4、容量足够；先做可恢复备份并在隔离环境验证；约定停机窗口，停止 API、缩略图 Worker 和 PostgreSQL 后复制完整数据目录，核对文件与权限，再将 `POSTGRES_DATA_DIR` 指向 ext4。原目录保留作只读回退依据；新目录开始接受写入后，不能直接切回旧目录而不处理增量数据。
2. 在接近线上数据量且有并发评分的环境测试缓存配置。8 GB 容器可从 `shared_buffers=2GB`、`effective_cache_size=6GB` 作为候选起点，观察内存、检查点、WAL 和评分延迟后再定值；这些数值尚未线上验证。
3. 先核对两次线上失败作业的实际任务、回测和评分明细，确认项目统计与实际数据是否一致。核对前不得重新执行整批分配，也不得按 97% 进度推断缺口。
4. 部署代码后用小项目观察 `task_generation_batch` 日志与统计刷新重试次数；在接近线上负载的测试库再比较 100、500、1000 条批量。验证之前保持 100。
5. 索引调整单独进行：先收集足够长时间的查询计划和索引使用数据，再决定是否合并或删除。扫描次数为零的索引只能列为候选，不能直接移除。

本次没有修改线上数据、索引或服务配置，也没有运行线上写入基准。

## 代码侧进一步优化（线上仍只读）

V4 分配器每条 `INSERT` 固定 100 个任务，原先每条任务语句所在批次都要单独提交。现已在本地增加独立的 `TASK_WRITE_TRANSACTION_SIZE`：可以保持每条 SQL 100 个任务，把例如 500 个任务的五组语句放入同一事务，减少提交次数，同时避免扩大单条 SQL 的参数数量。默认仍为 100；只有记录到线上 `commitMs` 占比较高时，才值得尝试 500。约 4 万条基础任务时，100 与 500 的提交次数分别约为 400 与 80，实际节省时间取决于线上每次提交的耗时。

本地真实生成路径以 100 个任务为单条语句、总计 10000 条（含 5% 回测）测试：100 个任务/事务耗时 850 毫秒，500 个任务/事务耗时 1143 毫秒。测试库位于本机 ext4，提交耗时仅占约 12–33 毫秒，不能代表线上 FUSE 的提交成本；因此没有直接提高默认值。两种配置的生成数和项目统计均为 10000。

线上 `rating_tasks` 的 32 个索引中有 14 个累计扫描次数为零，合计约 8.3 GB，存在明显的写入放大候选项。删除索引属于数据库结构变更，需逐个核对管理端查询计划、备好重建语句并灰度移除。一次本地未配对试验中，删去六个候选索引并未观察到提速；测试数据增长和缓存变化使这个结果不能用于推断线上收益。当前不把删索引作为已经验证的加速手段。
