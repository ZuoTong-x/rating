# 本地表结构与索引审查（2026-11-18）

本记录使用独立本地库 `rating_optimization_test_full_20261118`，并对当前线上 v54 执行只读元数据查询。生产库未写入。小样本查询计划不能推断生产大表索引的取舍。

## 已确认

- `schema_migrations` 记录 `0001`、`0002`、`0003`；编译后的迁移程序再次执行成功，没有重复应用 SQL。
- `project_packages` 的 `(projectid, packageid)` 主键覆盖旧同列索引；迁移 `0003` 已删除该重复索引，保留反向 `(packageid, projectid)` 和按项目创建时间的索引。
- 本地 `rating_tasks` 有 34 个索引（包含主键和唯一约束索引）。部分索引左前缀相近，但排序列、过滤条件或覆盖的查询不同。未发现另一个与主键完全同定义的索引，因此暂不删除。
- 当前线上 v54 尚无 `schema_migrations` 和 `thumbnail_subject_stats`，与迁移前状态一致；`rating_tasks` 有 32 个索引，总约 16 GB。六张关键业务表的 78 个列名与本地迁移后结构逐一一致。这个比对只验证列名，不能替代约束、触发器和数据一致性检查。
- 上述三张表的索引名称比较中，线上没有本地缺失的索引；线上多出计划由 `0003` 删除的 `idx_project_packages_project_package`（约 120 kB），以及旧索引 `idx_rating_tasks_version_updated_project`（约 258 MB，当前统计扫描次数为 0）。后者仍保留：现有打分人任务查询按 `updatedat` 排序，但是否需要此索引须用线上只读查询计划判断，不能仅凭零扫描删除。
- `0001` 旧库接管检查所需的 32 张业务表，线上全部存在。线上另有历史修复备份表；迁移不会使用或删除这些备份表。
- 本地项目的主图包字段 `projects.packageid` 均有对应关联记录，`scorer_task_stats` 未发现不存在的项目。字段仍有双重事实来源；后续约束改动须先核对生产历史数据并采用兼容迁移。
- 已初始化的 `thumbnail_subject_stats` 与 `thumbnail_jobs` 明细按图包统计一致。缩略图列表使用汇总表和分页读取；最近五分钟完成数仍需扫描该时间窗口的任务。

## 关联关系与命名

- `projects.packageid` 保存首个图包，`project_packages` 保存完整关联；创建与编辑服务同时写入两处。数据库尚未强制首图包一定出现在关联表。当前本地样例一致，生产历史数据需先只读核对，再决定是否补约束或收敛为单一来源。
- `task_generation_jobs.subjectid` 的外键实际指向 `projects(id)`；这是旧命名，不是图包外键。代码和 API 仍同时提供 `subjectId`/`projectId` 兼容字段。本轮不做列重命名，以免破坏正在运行或历史作业的读写。
- `scorer_task_stats` 和 `scorer_scoring_stats` 以打分人名称为键，没有直接指向 `users(id)` 的外键。改用用户 ID 需要双写、历史映射、分批回填与 API 兼容，不能作为本轮索引清理顺手实施。

## 回退口径

- `0003` 只移除了重复索引；若旧查询计划在真实数据上明显退化，可另建增量迁移恢复该索引，生产环境使用适合大表的非阻塞建索引流程。
- `0002` 只增加汇总表和触发器；旧 API 可以忽略新增结构。若汇总异常，暂停依赖汇总的管理端查询并重算该图包统计，不修改 `thumbnail_jobs` 事实行。
- 迁移版本记录保持不可变；回退用新的编号迁移，不编辑已经应用的 SQL。
